# Travel Map 与足迹渲染设计

**状态：当前设计边界，2026-10-15 整理。** 现行实现以 iOS MapKit、Web Leaflet 和 FastAPI Footprint domain 为基础。本文只描述稳定语义和已落地的第一轮渲染规则；尚未完成的视觉、真机与性能验收见 [实施计划](implementation-plan.md)。[清理前完整设计](../../../archive/footprint-ios-design-pre-cleanup.md)保留历史细节，不能代替当前代码。

## 产品与数据语义

Travel Map 展示用户自己的当前位置、旅行足迹点位和主动打卡，支持当前旅行与有限历史行程回顾。底图、手势和投影复用地图 SDK；Vago 绘制个人足迹数据。Web 与 iOS 共享足迹语义，但交互按各自场景设计。

`TravelFootprint` 是 GPS 与手动打卡的统一空间事实实体，通过 `footprint_type` 区分 `AUTO_GPS` 和 `MANUAL_CHECKIN`。两者都可以在可信连续段中成为路线顶点；手动打卡还应有独立、可点击的标记。路线“经过打卡”是正常设计，打卡不能跨越已判定的段边界。原始坐标、时间、类型和段标识不随 UI 平滑或简化改变。

## 采集、同步与归属

- iOS 仅在用户明确开始后进行前台定位；当前记录状态应可见，不暗中启动后台定位。
- GPS 先进入按账号隔离的本地待传队列，再按最多 100 条/批同步。客户端事件键保持稳定，服务端按认证用户与事件键幂等处理；成功响应后才清理对应待传项。
- 当前行程与历史浏览分离：查看历史地图不能改变 GPS 或打卡的写入 Trip。已结束行程只读，但允许补传此前离线采集的 GPS。
- 个人位置默认私有；服务端按认证用户验证 Trip 归属，原始 GPS 不进入普通日志。AI 可以读取受授权的足迹点位事实，不能伪造或改写它们。

## 轨迹渲染

处理顺序是：同 Trip 合并本地与远端足迹点位、按稳定事件键去重、按发生时间排序、判断点质量、判断连接可信度、构建连续段，再在显示层选择线和可见自动点。劣质 GPS 点可作为断线依据，但不能先删掉它再连接两侧。

当前 iOS / Web 共用的连接启发式边界：显式段 ID 改变（包括有 ID 与无 ID 的边界）、非递增时间、超过 2 小时停顿、超过 20 分钟且位移大于 1 公里、单次位移大于 5 公里、推算或上报速度超过 55 m/s，以及无效坐标或精度超过 100 米的自动 GPS，均不得跨越连接。两个相邻点都没有段 ID 时，才按时间和空间规则推断历史连续性。阈值须由真实行走与车行数据继续校准。

路线使用柔和底描边与主线；少量自动 GPS 点显示采样来源，按地图投影后的约 22 px 最小间距筛选，并优先保留段首尾与明显转角。隐藏自动点仅改变显示，不改路线或打卡。地图自动取景使用可信路线点与有效打卡，不被劣质 GPS 拉远。

iOS 仅在边长、转角和偏差受限时使用 Catmull–Rom 显示插值，否则保留圆角折线；Web Leaflet 的 `smoothFactor` 用于折线简化，不等同曲线平滑。插值不是道路匹配，也不是用户实际走过的额外事实。历史段的缓存、增量重绘、视口查询或服务端聚合只在实测性能需要时引入。

## 打卡与未来能力

打卡创建需要用户确认的当下位置，并绑定进行中的 Trip；30 米内重复打卡由服务端拒绝。用户可编辑主动输入的名称与备注，不能借编辑改写足迹坐标或发生时间；已结束行程保持只读。现行入口和字段见 [Footprint API](../../../API/footprint-service.md)。照片上传、离线打卡、反向地理编码仍需独立设计和验收。

World Fog / Explored Area 是基于已保存旅行事实的未来实验，不是现有地图能力；不得将未加载的历史数据解释为“未探索”。只有用户明确要求时才推进 Fog 实现。探索区域应从有效足迹点位重建，不能用断段之间的插值开辟虚假走廊。
