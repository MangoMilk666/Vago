# 阶段 4：地点与路线来源

> 更新于 2026-10-28。D05 本轮仅要求 Web 与 iOS 的中国大陆地点搜索和路线规划可用。Web 使用高德；iOS 使用设备原生 MapKit。Apple Maps Server API 凭据暂不可用。下列“已接入”仅指代码路径，真实服务和客户端能力仍按各自验收项确认。

**当前状态：主要开发已完成，iOS 真机验收未通过。** Web 中国大陆规划候选闭环已验收；iOS 中文地点搜索在真机仍会于城市定位步骤失败，完整保存交互未验收。此问题暂时搁置，不将模拟器通过等同于真机通过。

## 已接入

- Vago 后端增加认证后的地点搜索、路线候选和地图预览接口：`POST /api/v1/agent/planning/places/search`、`POST /api/v1/agent/planning/routes/search`、`POST /api/v1/agent/planning/routes/preview`。大陆使用高德；境外 Apple Maps Server API 代码路径因无凭据暂不可验收。密钥仅由服务端环境变量读取。
- 延续 wkf 的“先找地点、再获取多个路线候选、选择一条路线”的流程。返回路线耗时、距离、来源、坐标系、查询时间和十分钟有效的 `routeChoiceId`。该 ID 由服务端签名并绑定当前用户、地点 ID、路线耗时与来源；候选版本创建或重新校验时核对签名。过期或被修改的引用不能通过来源核验。
- 高德地点/路线使用 GCJ-02，Apple 使用 WGS84。坐标系不匹配直接拒绝；规划结果不得作为实际足迹保存。Apple Maps Server API 未提供公交路线查询，境外公交返回 `MAP_MODE_UNSUPPORTED`，不会伪造路线或改用驾车时长。
- 候选 `content.days[].items[]` 如使用路线，应提供 `latitude`、`longitude`、`coordinateSystem`；对应 `legs[]` 应带 `mode` 和路线响应中的 `provider`、`routeChoiceId`、`routeDurationMinutes`、`queriedAt`。服务端同时核对路线端点坐标、用户归属、方式和耗时，不能把 A 点的路线引用挪给另一组地点。
- 无凭据、上游不可用、配额限制、无路线及不支持地区/交通方式均返回明确错误。候选仍受阶段 3 的时间、预算与硬约束检查约束。
- 三个外部查询入口按认证用户共用每分钟 12 次的 Redis 配额；配额服务不可用时直接告知，避免意外耗尽共享地图服务额度。

## 按 D05 调整后的验收

1. **Web 中国大陆：** 高德 Web 服务 Key 已在本机 FastAPI 配置。真实地点、步行/驾车/公交路线、短期路线引用及静态地图预览已通过服务层验收；登录后的浏览器交互、候选时间线保存与刷新回读已通过实测。异常与配额提示仍需分别验收。
2. **iOS 中国大陆：** Agent 聊天页已接入设备原生 MapKit 地点搜索、路线候选和可交互预览；可将设备路线以注明未核验的文字带入聊天输入框。保存候选时，iOS 用地点名称与位置匹配服务端高德地点，服务端重新查询同一组地点与交通方式的路线，并签发归属当前用户的短期 `routeChoiceId`；随后保存到当前会话并回读版本。杭州地点与步行路线通过模拟器真实请求；完整保存交互及真机体验仍待验收。
3. **共同边界：** 设备的 MapKit 折线仍是独立预览。候选中“服务端已核验”的路线是 FastAPI 重新查询的高德路线；若地点无法匹配或服务端路线不可用，iOS 显示错误，不把 Apple 路线登记为已核验。设备端 `MapKitRouteCheck.isDisplayable` 只判断预览可绘制。正式候选仍遵循 D04；高德 GCJ-02 与 Vago WGS84 的视觉核对仍需完成。

境外地点、路线及地图预览不纳入本轮验收；Apple Maps Server API 凭据不作为本轮前置条件。

## 本机真实服务验收记录

2026-10-26 运行 `cd services/vago-ai && PYTHONPATH=. .venv/bin/python scripts/verify_amap_live.py`。公开景点“上海外滩 → 东方明珠广播电视塔”的地点搜索成功；步行、驾车、公交分别返回 1、1、3 条路线。三种路线的用户、端点、坐标和耗时签名引用均通过校验。路线耗时随高德实时结果变化，不作为固定断言。

2026-10-27 iOS 补充：Agent 页新增“地点与路线”入口，弹出的原生地图面板支持选起终点、切换交通方式、比较候选和查看真实路线折线。此数据留在设备内存中，关闭面板即消失；带入聊天时作为用户输入并明确注明来源。设备端 MapKit 查询不生成 FastAPI 签名 `routeChoiceId`，阶段 3 的路线硬约束仍保持 `unverifiable`。iOS Simulator 构建通过；杭州两所大学的地点搜索与步行路线真实请求通过。新加坡验证中发现模拟器地图搜索将英文地名误命中香港、安徽，并将中文“新加坡”误命中云南的同名地点；现按所填地区中心筛选地点，并拒绝城市归属不明的结果。该模拟器上的新加坡路线尚未验收通过。真机测试尝试因设备不可用而未启动，Xcode 报告需解锁设备并通过数据线或同一局域网连接；仍需在真机与目标地区复测。专门的真实服务测试保留为显式开启项。

同日真机反馈修正：原实现先用 `MKLocalSearch` 查城市，再强制要求结果带有匹配的 `locality` 或 `country`；真机对“杭州”未返回符合该条件的字段，导致每个地点查询都提前失败。现直接以“地区 + 地点”查询，并仅展示返回地址能确认归属该地区的候选。模拟器真实请求再次验证：杭州两所大学地点与步行路线、`Zhejiang University` 和 `Hangzhou Olympic sports center` 英文地点查询均通过。新加坡请求在当前模拟器地图服务仍返回无结果，不将境外能力记为已验收。真机改动后的查询需再次实测。

## 地点搜索与路线计算分开验收（2026-10-27）

Vago 的规划能力不能以 `MKLocalSearch` 成功作为所有路线计算的必要条件。用户在地图上选点、使用已有行程地点或当前定位时，已经有可确认的坐标；客户端可以用两个坐标构造 `MKMapItem`，直接请求 `MKDirections`。此路径只验证设备能否得到路线，不依赖地点名称搜索，也不改变现有业务页面、FastAPI 契约或正式候选的来源核验规则。

已在 `RoutePlanningLiveTests.testWalkingRoutesFromFixedCoordinatesWithoutPlaceSearch` 增加需显式开启的真实服务测试，分别以杭州、新加坡、纽约的固定公开地点坐标请求步行路线。iPhone 17 Pro 模拟器（iOS 26.5、当前本机网络）实测：杭州返回可绘制路线；新加坡和纽约均在 `MKDirections.calculate()` 返回 `MKErrorDomain/2`，系统说明为“路线不可用”。这证明本机这两组路线问题不只出在 `MKLocalSearch` 或 Vago 的搜索结果过滤；单次模拟器结果不能推断其他设备、网络和所有境外地区的可用性。真机测试尚未完成：当前 `VagoIOSTests` 真机签名缺少 Development Team，测试未启动。

上述跨地区对照属于历史诊断，本轮不再要求境外复测。中国大陆真机验收仍分别记录「坐标来源 → 地点搜索（如需要）→ 路线请求 → 地图绘制」，并核对来源、坐标系、交通方式和查询时间。供应商结果的展示和缓存遵守其使用条款。

## 配置与来源

环境变量见 `services/vago-ai/.env.example`。Apple 服务端私钥当前无需配置；未来启用时也只进入服务端，不放进客户端或仓库。当前 `routeChoiceId` 是短期签名引用，不是 Apple 或高德的永久路线 ID；正式 Plan 的长期来源保存与重新查询还需在阶段 7 的写入设计中复核。

接口与展示限制以高德路径规划 API、Apple Maps Server API 路线接口及 Apple 开发者协议为依据。
