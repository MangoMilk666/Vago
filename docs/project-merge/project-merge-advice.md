# Vago 与 travel-assistance-wkf 合并评估及分阶段落地建议

> 更新于 2026-10-15。基于本地 Vago `2f29117`、travel-assistance-wkf（下称 wkf）`35c4584` 及当前工作区代码；未执行两项目端到端运行。本文区分代码已有能力、评测结果与合并目标。所有项目合并信息在本文维护，本次不新增其他文档。

## 1. 总体决策

以 **Vago 产品、仓库、认证、领域服务、MySQL 正式旅行记录和 Web/iOS 客户端**为主干，按模块吸收 wkf 的规划计算、外部地点与路线查询、会话交互和 Agent 编排经验。先完成“**生成候选方案 → 展示依据与校验结果 → 用户确认 → 写入 Vago 正式 Plan/Itinerary**”的闭环；运行中 Trip 重规划、图记忆和领域 Agent 再分别验证。

不直接拼接两个对外 FastAPI、两套前端和多套业务真相源。wkf 的 `chat_id`、`user_id`、`group_id` 不能作为 Vago 授权依据；wkf `itinerary_results` 是会话候选版本的设计参照，不能直接当作 Vago 正式行程。复制代码前须确认 wkf 代码及第三方资产的复用权利；当前仓库根目录未见 `LICENSE`。

首期产品形态按用户意见确定：**Vago 的聊天输入和消息流保持主界面；Agent 答复引用可展开的地点、路线、地图和行程候选预览组件**。不照搬 wkf 三栏页面，也不让预览长期挤占输入区。Web 先完成规划与确认闭环，iOS 按旅行中使用场景接入。

## 3. 对已提出个人意见的处理

| 意见 | 处理结论 |
| --- | --- |
| 两边后端类似，冲突以 Vago 优先 | 同意。Vago 的身份、领域模型、正式写入和客户端兼容性优先；wkf 的算法和控制流按接口改造，避免长期双后端。 |
| PostgreSQL 数据可并入 MySQL | 对需要保留、能确认归属和语义的 wkf 候选版本可以迁移；先做字段映射、校验和试导入。没有理由为此保留第二套正式 PostgreSQL。无归属会话不能直接导入用户账号。 |
| Neo4j 先保留，未来讨论它与 Qdrant | 同意保留作实验性、可重建的个人记忆投影。Neo4j 侧重关系和时态事实；Qdrant 用于非结构化知识语义检索，两者不是等价替代。待同一任务对照后决定共存、收缩或弃用。 |
| wkf Agent 机制可复用，先单 Agent | 同意，但拆出澄清、取消、预算、工具白名单、候选提交等能力按需接入；域委派需单独举证。 |
| 中国大陆与境外可用不同地图依赖 | 同意，规划数据通过 provider 适配层输出统一契约。高德可用于大陆候选；境外 provider 尚未选定，应按覆盖、授权、成本和质量决定。地图底图仍由 Web/iOS 现有组件承载。 |
| 可复用 wkf 的 MCP 连接代码思路 | 可作为未来受控外部工具适配方案。先用直接 provider API 完成路线闭环；MCP 需要时再接，且默认关闭不需要的连接。 |
| 不沿用三栏；聊天答复引用资源预览 | 采纳为目标交互。答复内引用有稳定 ID 的资源卡片，展开后可看详情/地图/候选版本；保持输入区宽度和消息可读性。 |
| JSONL 聊天存储是否更省 | 现有 wkf 实现每次保存全量重写，不能据此判断更高效。Vago MySQL 支持归属、索引、分页和事务，继续作为生产存储；若担心长会话成本，应实测读取、写入、压缩、备份和并发，再选摘要或归档。 |
| Vago 的 tooling 事件流可视化 | 延续已有公开 SSE 事件，增加阶段、工具名、状态、关联的 proposal/version/resource ID；进度是展示，持久化状态由可回读 API 保证，不暴露模型内部推理、密钥或原始 GPS。 |

## 4. 合并时固定的契约

1. **身份与隔离**：所有 `conversation_uuid`、候选版本、正式 Plan/Trip、地图缓存、图记忆均绑定服务端认证得到的 `user_uuid`；请求体不接收可决定归属的 wkf `user_id`。列表、详情、澄清、取消、事件重连、版本读取和确认写入分别校验归属。
2. **候选与正式记录**：`PlanningBrief` 表达当次目标、日期、人数、预算、硬约束和已确认偏好，不覆盖正式 Plan。`PlanProposal` 为不可变候选版本，含 `conversation_uuid`、可选目标 `plan_uuid`/`trip_uuid`、版本、状态、每日项目、路线选择、来源/查询时间、价格/币种/估算标识、警告、校验结果和创建时间。仅用户确认后的专用命令可调用 Vago Travel Service 持久化正式记录；重复确认需幂等，源候选版本需可追溯。
3. **来源与坐标**：外部地点和路线保存 provider、外部 ID、查询时间、坐标系、时区及失效/估算标识。高德候选和 Vago WGS-84 足迹、MapKit/Leaflet 展示之间需明确转换与误差验证；任何计划路线不得进入 `travel_footprints`。地图源与路线源可以不同。
4. **约束与决策**：对日期/时区、停留与换乘时间、地点顺序、显式禁忌和可计算预算进行确定性检查。结果分 `pass`、`fail`、`unverifiable`：`fail` 阻止正式写入；用户明确列为硬约束的 `unverifiable` 要补证据、修正或显式说明并重新确认，不能默认通过；软性未知以醒目警告展示。Agent 文本不能覆盖校验结果。
5. **对话与事件**：沿用 Vago `AgentConversation`/`AgentMessage` 和公开 SSE 事件。事件携带会话/turn、trace、序号、阶段与关联资源 ID；工具执行、澄清、候选就绪、失败/取消、确认结果有明确状态。断线重连读取持久化会话、候选和确认状态，不依赖历史 SSE 重放。
6. **工具与记忆**：Agent 使用有 schema、超时、权限和成本预算的内部 Domain Tools 或受控外部适配器，不直接访问通用 SQL。Vago 结构化事实/明确偏好优先；Neo4j 若接入，仅作为按 `user_uuid` 隔离的可选投影，保留来源、确认状态、纠错和删除路径，推断内容不能改写 GPS/打卡或用户确认偏好。

### 数据映射重点

| wkf 数据/能力 | Vago 目标 | 迁移规则 |
| --- | --- | --- |
| `chat_id`、JSONL session | `AgentConversation`/`AgentMessage` | 新会话由 Vago 生成 ID；旧记录仅在可证明归属且有迁移需求时导入。压缩摘要可单独借鉴。 |
| `TripPlan` 表单 | `PlanningBrief` 或 Plan 创建输入 | 用户需求与正式旅行记录分开；明确偏好不由表单抽取结果静默覆盖。 |
| `itinerary_results` 与 `submit_itinerary_plan` | MySQL `PlanProposal` 版本 | 保留不可变版本、回读和先写后通知；把 wkf “提交”改为候选提交，不直接创建 Vago Plan。 |
| `placeRef`、`routeChoiceId` | 外部地点/路线引用 | 与 provider、坐标系、查询时间和来源绑定；过期时重新查询，不以模型编造 ID 代替。 |
| Episode/Entity/Edge | 可选 Neo4j 用户记忆投影 | 仅在身份绑定、重建、纠错、删除和效果比较过关后接入生产；不作为唯一事实库。 |
| 域 Agent 报告 | 结构化观察/资源引用 | 附完成状态、证据与未解决项；主 Agent 接收的摘要不能丢失关键候选和约束。 |

## 5. 更细的分阶段落地顺序

每阶段单独可验收、可回退；编号表示依赖顺序，未通过门槛不把下一阶段标为完成。阶段 0–7 构成规划闭环，阶段 8–11 是扩展或独立试验。实现单元可再拆 PR，但一个 PR 不应同时改身份、全量编排、正式写入与双端 UI。

| 阶段 | 范围和交付 | 明确不纳入 | 合并/验收要求 | 指导信息文件 |
| --- | --- | --- | --- | --- |
| **0. 基线与复用边界** | 锁定双方提交与测试命令；盘点调用链、第三方许可、wkf 作者授权、可迁移数据归属；建立无密钥/真实位置的规划样例。 | 复制大模块、部署 wkf API、导入本地聊天/记忆。 | 代码复用权利和第三方条款明确；样例可重现；Vago 现有 Web/iOS/领域测试有基线。许可未解决时只可独立重实现思想。 |  |
| **1. 身份和领域映射** | 列清 wkf 表单、地点、路线、时间线、版本到 Vago Plan/Trip/Itinerary 的逐字段映射与缺失语义；定义认证用户、会话、目标旅行和候选的归属；确认时区、币种、坐标契约。 | AgentLoop、Neo4j、前端大改。 | 用至少一例新 Plan 和既有 Trip 场景检验映射；所有入口有可执行双用户测试；未定义字段不静默丢弃。 |  |
| **2. 候选持久化与查询 API** | 在 Vago MySQL 建候选版本及必要的 Brief/资源引用；提供创建、列举、按版本读取与状态读取的领域/API 路径；服务端生成版本和关联 ID。先以固定样例写入。 | 正式 Plan 写入、PostgreSQL、JSONL 替换对话库。 | Alembic 升降级/回滚路径明确；并发版本不重号、重复提交幂等；另一个用户无法读/改/确认候选；刷新后可回读。 |  |
| **3. 时间线与约束校验** | 把 wkf `build_itinerary`/`dryRun` 的可复用逻辑及 `ItinerarySnapshot` 检查适配到 Vago 候选；定义适用规则、`fail`/`unverifiable`/警告及来源缺失处理；校验结果随版本保存。 | LLM 自行裁决硬约束、直接“提交即正式保存”。 | 多日、跨日时区、路线缺失、冲突、禁忌和预算缺证据反例通过；保存关口重新校验选中版本；失败或硬约束未知不静默晋级。 |  |
| **4. 外部地点与路线 provider** | 按 Vago 认证和配额边界适配 wkf 高德搜索/路线候选/选路缓存；统一地点与路线输出，记录坐标系、来源、时间和失效策略；境外 provider 先保留接口与降级策略。 | 替换 MapKit/Leaflet、把路线写入足迹、同时接所有国家 provider。 | 大陆至少一条真实路线能查询、选定、经时间线计算并预览；WGS-84 与 provider 坐标转换在地图上核对；密钥只在服务端，失败/限额有可理解的结果。 |  |
| **5. 单 Agent 规划与交互** | 在 Vago Runtime 中按需接入 wkf 的工具循环、澄清/恢复、取消和预算控制；工具仅产出 Brief/Proposal 或读取领域事实；公开进度映射到现有 SSE。 | 默认启用域委派、MCP、wkf 未认证路由或文件会话库。 | 一次规划可多轮澄清并产出候选；取消后不产生正式写入；超时/服务失败有终态；工具与事件按用户隔离，断线能查持久化状态。 |  |
| **6. Web 聊天内资源预览** | 在现有 Vago AI 页面展示引用式地点/路线/地图/候选卡片、版本切换、校验警告和来源；答复文字引用稳定资源 ID，展开预览不覆盖聊天输入。 | wkf 三栏前端、整站升级 React/Vite、正式确认写入。 | 流式与历史消息均能恢复同一卡片；用户看得清来源、估算、硬约束状态和版本；窄屏输入体验可用。 |  |
| **7. 用户确认与正式 Plan 写入** | 增加专用确认命令，按认证用户、候选版本和当前目标状态再次校验，经 Vago Travel Service 创建/更新正式 Plan/Itinerary；保存候选到正式记录的关联与审计信息，回读结果。 | Agent 自动确认、修改正在进行中的 Trip。 | 用户拒绝/超时/冲突时正式数据不变；重复确认幂等；部分失败不留半成品；写入后 Web 可读取对应正式行程。此阶段才称首个端到端闭环。 |  |
| **8. iOS 适配** | 基于阶段 7 的同一 API，展示候选/已确认计划、警告和来源；按移动端需要决定是否加入确认按钮和澄清回复。 | 复制 Web 编辑器、在 iOS 执行 Agent Runtime。 | 同一用户跨端版本一致；若提供确认，遵循同一幂等/审批规则；旧 iOS 足迹、打卡和行程展示可用。 |  |
| **9. 进行中 Trip 重规划** | 生成“只改未来剩余日程”的候选差异，引用当前 Trip 与版本；校验时间/预算/已发生事实后展示变更，再经领域服务批准应用。 | 改写过去日程或 `TravelFootprint`、从建议直接静默写库。 | 拒绝后无变化；批准后差异可追溯并回读；并发修改触发冲突重算；足迹及已完成日程不受影响。 |  |
| **10. Neo4j 记忆对照试验** | Neo4j 先保留在隔离环境；以可重建投影连接 Vago 已授权事实/对话，比较“Vago 结构化上下文 + 可选 Qdrant”与“再加图记忆”的同题表现。 | 全量 MySQL 迁移、将推断事实写回原始旅行数据。 | 预先固定跨旅程偏好、时态矛盾和纠错样例；记录质量、来源正确率、双用户隔离、删除传播、时延与成本。未达门槛维持实验状态；共存或替换 Qdrant 另做决策。 |  |
| **11. 域委派 / MCP 按证据启用** | 在单 Agent 基线之上，针对确需浏览器、长上下文或并行检索的任务分别试域委派；有明确 provider 需求时适配 wkf MCP 连接模式。 | 因“更先进”默认多 Agent 或默认连接 Playwright/Exa。 | 同题对照质量、证据保真、延迟、token/费用与失败率；用户隐私、工具授权、超时及关闭开关可验证；未获收益不进默认链路。 |  |

**建议的首个实现 PR**：只覆盖阶段 1 的可执行契约和阶段 2 的最小候选版本持久化/读取，使用固定样例与双用户隔离测试。时间线/约束校验作为下一 PR，随后才接地图、Agent 和界面。这样先固定“候选 ≠ 正式记录”的关键边界。

## 6. 贯穿各阶段的发布门槛

- **数据与权限**：每个新增 API/工具用两个账号验证列表、详情、版本、澄清、取消、确认和缓存；客户端提供的 `user_id/group_id` 不能决定归属。
- **兼容与迁移**：采用 Vago Alembic 管理 MySQL schema；逐调用方切换并回归 Web/iOS。若迁移历史 wkf 数据，先确认来源、账号映射、去重、备份及撤回路径。
- **事实边界**：规划路线与实际 `TravelFootprint` 分开；来源、估算和不确定性在 UI 可见。地图 provider 切换不改变用户足迹坐标事实。
- **可观测与恢复**：公开事件可以显示过程，但候选、校验和正式写入结果须可独立回读；不记录原始 GPS、Prompt、模型内部推理或密钥到普通日志。
- **验收口径**：wkf 评测与单元测试证明相应代码路径可运行，不等于 Vago 真实场景已验收。每阶段用适配后的契约测试和一条完整用户路径验证，未通过不扩大默认流量。
